3. Confirmed static findings

CD-IR-01: High, release blocker. The Free cap and Plus gates fail open outside QA builds.

src/plus-entitlement-runtime.ts:44-52 enables enforcement only when configured && isLocalTesting, or when the qaFreeMemoryLimit flag is set.
src/plus-memory-limit.ts:10 and src/plus-feature-gate.ts:5 return immediately when enabled is false.
In any build outside those QA identities, there is no 20-memory cap and no backup gating.
Rationale: the superbatch report says production Free entitlement “remains restricted”. The code does not show that.
Fix: enforce by default, make an unconfigured release build fail closed or refuse to start, and add a test that asserts this on the release configuration.
Verify: a release-configuration build, 21st save and backup attempt on a Free account, on both platforms, in store sandbox.

CD-IR-02: High. No production purchase or acknowledgement path exists.

app.config.js:3-6 throws for any production environment.
PlayOwnershipModule.kt:26 requires the test flag, and the only purchase function is purchaseForLocalTesting.
On iOS, PlusStoreReader.swift:36-37 throws checkoutDisabled in release builds.
plus-entitlement-runtime.ts:28 only creates the acknowledgement coordinator when isLocalTesting is true.
Per the Google guidance above, a Play purchase that goes unacknowledged for 3 days is refunded automatically, so this must become a release gate.
The only entitlement check is client-side signature verification (PlayOwnershipModule.kt:85-88). That fits your no-cloud rule but should be recorded as an accepted residual risk.
Fix: build the production path (checkout, acknowledgement, Restore Purchases) and test it only in sandbox.
Verify: sandbox purchase, kill the app mid-purchase, relaunch, confirm acknowledgement.

CD-IR-03: Medium. A paying user is blocked whenever entitlement can’t be verified.

plus-entitlement-store.ts:30 sets status to error while the entitlement stays at its initial free.
plus-memory-limit.ts:13-14 then throws “Unable to verify Plus right now”. A last-known Plus state is held only in memory, so it is lost on restart.
Android adds a 3-minute timeout and a disconnect failure (PlayOwnershipModule.kt:101-103).
A paid user over the cap cannot save, back up or restore while the store is unreachable. Data is kept, but they are locked out of Plus features.
Fix: persist a non-secret last-verified-Plus cache, re-verify in the background, and never downgrade on an error.
Verify: verified Plus, airplane mode, cold start, 21st save, on both platforms.

CD-IR-04: Medium. Free-tier data recovery is thin, and restoring your own backup is Plus-only.

plus-access.ts:12-14 gates both full-backup and restore-backup behind Plus.
app.config.js:34 sets allowBackup: false. I found no iOS backup-exclusion setting, so iOS behavior is unverified.
A Free Android user who loses or replaces a phone keeps only the text report, which has no photos.
A refunded or revoked Plus user cannot restore their own earlier archive.
This matches your approved tiers, so I’m challenging the policy rather than the code. It conflicts with your stated values of privacy and durable data.
Recommendation (owner decision): allow Free restore of a user’s own archive into available slots, and keep full export as the Plus value.
Verify: a policy test for restore at 19, 20 and 21 memories.

CD-IR-05: Medium. The privacy-hardened reminder module is unused, and the live path is less private.

Nothing in src, tests or plugins references casitadex-reminder-alerts. Its generic body text (“Open CasitaDex to review your reminders.”) and VISIBILITY_PRIVATE therefore never run.
The live path is src/reminder-alerts.native.ts:43. It puts the reminder title in the notification body, with no lock-screen privacy setting.
The unused module still ships native code, including a BOOT_COMPLETED receiver.
Fix: pick one implementation. If the live one stays, add lock-screen content control and Android private visibility.
Verify: lock-screen screenshots on both platforms.

CD-IR-06: Medium to High. Repeating reminders stop firing if the app isn’t opened.

reminder-alert-plan.ts:103,123 arms at most 6 occurrences per reminder and 48 in total.
Rescheduling happens only when reconcile runs (standalone-reminders.native.ts:26,40,51,56).
A daily reminder therefore goes silent after roughly 6 days without opening the app.
The success message at reminder-alerts.native.ts:56 does not disclose that limit.
The cap of 48 does respect the iOS limit of 64.
Fix: use repeating triggers where the platform allows, or disclose the window honestly in the UI.
Verify: a daily reminder with the app untouched for 7 days, using simulator clock advance.
