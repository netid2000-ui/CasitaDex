Review of the enlarged-text header change (Option A)

This is a static review only. I ran nothing, and the native observation of the iOS occlusion is yours, not mine.

Research
React Native stickyHeaderIndices.
The prop takes child indices that dock to the top while scrolling, and [0] pins the first child. It does not work with horizontal. I could read this text only on the Amazon Vega fork of the RN docs (https://developer.amazon.com/docs/react-native-vega/0.72/scrollview). The reactnative.dev page (https://reactnative.dev/docs/ScrollView) came back truncated for this prop.
Passing [] therefore means “no sticky child”, so the change is a correct use of the API.
I found nothing documenting how an iOS sticky header measures its own height or whether it is unreliable under font scaling. Treat the cause of the overlap as unknown.
Apple guidance. The HIG typography page and the WWDC Dynamic Type session (https://developer.apple.com/videos/play/wwdc2024/10074) say to adapt layout at larger accessibility sizes while keeping the default layout at smaller sizes, and to test at the largest sizes. App Store Connect’s Larger Text criteria say the same (https://www.developer.apple.com/help/app-store-connect/manage-app-accessibility/larger-text-evaluation-criteria). None of it addresses sticky headers specifically, so it supports the direction but not this exact fix.
Source observations
What the diff does. In src/figma-first/FigmaReminders.tsx, stickyHeaderIndices={compactHeader?[]:[0]} makes the first child scroll at enlarged text. That matches Option A. The app title and bottom navigation are not inside this ScrollView, so the diff leaves them alone, but I can’t see their code.
The 2×2 tab layout (flexBasis:"45%" when compact) is sensible. Tabs keep minHeight:48.
Challenges
The test is a string match, not behavior (source-backed).
tests/reminder-header-accessibility.test.mjs only checks the source text for three patterns. It passes even if compactHeader is never true at runtime.
It also asserts const compactHeader=large||fontScale>=1.35, so changing the threshold would fail it for the wrong reason.
Fix: extract a pure usesCompactHeader(large,fontScale) and test the boundaries 1.34 and 1.35 and the large flag.
The trigger is scale-only (hypothesis).
The failing case was measured by position (toggle [18,346][384,441] inside the filter band [18,329][384,469]), which suggests the header band overlapped content below it, not just that text was big.
A threshold of 1.35 may not cover a small phone at 1.3, landscape, split-screen or Android display-size changes, where the header is tall relative to the viewport.
Alternative: switch off sticky when the measured header height exceeds a fraction of the viewport (for example 35%), in addition to the scale check.
Root cause not shown (hypothesis). If the overlap came from sticky-header measurement and not from header height, removing stickiness may fix the symptom only at the sizes tested. Native re-run needed.
Usability tradeoff (owner-accepted, noted). At enlarged sizes, “Add Reminder” and the filter tabs scroll away. Someone deep in a list must scroll back up. Option A accepts this. If it hurts, a back-to-top control or a fixed bottom action would help, but I’m not recommending a change.
