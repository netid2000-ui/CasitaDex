Research
iOS announcements. AccessibilityInfo.announceForAccessibilityWithOptions exists, and queue (behind existing speech) is iOS-only. By default an announcement interrupts current speech (https://reactnative.dev/docs/0.85/accessibilityinfo). The diff uses queue:true on iOS only, which matches this.
Android. In the RN commit that added the options, the Android branch just calls the plain announce (https://github.com/facebook/react-native/commit/4d1357918a4). The app skips Android here and relies on accessibilityLiveRegion.
Not retrieved: that accessibilityLiveRegion is Android-only, and anything from Apple’s announcement guidance. Those are my recollection, not research.
What holds up (source-backed)
Separate error and status state, both inside the scroll content (FigmaReminders.tsx). The earlier fixed message is gone from reminders.tsx.
runReminderFeedbackAction keeps phases apart. A failed refresh after a committed action sets status to the real result and adds refreshError, so it never claims the action failed. Warnings pass through verbatim, and test 1 pins that.
actionLock plus disabled Complete and Delete stops overlapping actions.
Objections
Stale success next to a new failure (source-backed).
On action failure, runReminderFeedbackAction only calls reportError. The previous status (“Reminder saved locally.”) stays on screen next to the new “Needs attention” error.
The second test pins [["error",actionError]], so it blesses this behavior.
Fix: clear status at the start of every action.
Feedback never clears (source-backed).
refresh never resets error or status, and reminders.tsx only clears them on a later successful action.
A “Unable to load reminders” or “Alert coverage could not be checked” message can outlive the problem, and a success message can sit there for hours across tab visits.
Fix: clear both on focus, and expire status.
Off-screen feedback for actions lower in the list (source-backed, usability).
Feedback now sits under the header, so tapping Complete or Delete on the 15th reminder shows its confirmation or failure off-screen. The old fixed message at least stayed visible, even though it cost 179 pt.
A successful Complete visibly removes the row, but a failure message at the top is invisible to a sighted user. Only iOS VoiceOver users get an announcement.
Options: scroll to the feedback on error, show a row-level message, or use an Alert for failures.
Warnings look like confirmations (source-backed). Strings such as “N existing alert(s) may still show titles” and “Notifications are off” come back as plain strings, so they render under the calm “Reminder update” style. A title-exposure warning should get the “Needs attention” treatment. A {level,message} result would fix this.
Android announcement reliability (hypothesis).
Repeating the same text (“Reminder saved locally.” twice) is not a state change, so a live region may stay silent.
Two live regions (error and status) changing together, as in a committed action followed by a refresh error, may speak only one.
Needs a TalkBack run. A changing key or counter would help.
Silent drop (source-backed edge). If a delete is confirmed in the alert dialog while another action holds actionLock, act returns with no message. The user confirmed something and nothing happens.
Fragility. Feedback is rendered only inside the onToggleTitles block, so a caller without that prop would show no errors at all. The privacy failure copy (“Review device notification settings”) blames notifications when the cause is a storage write.
Test gaps (benign)
Clearing status on failure, and clearing on focus or refresh.
Repeated identical messages.
The iOS-only and focused-only announcement guard.
The lock dropping a confirmed delete.
Feedback visibility without onToggleTitles.
The layout test checks source order only.

Native checks to run: VoiceOver queued announcements and TalkBack live regions, feedback visibility after acting low in the list, large text, light and dark contrast of the new boxes. None of these has been run.
